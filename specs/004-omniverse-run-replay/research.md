# Research: Omniverse Run Replay

The project owner decided on replaying recordings first with a live source prepared for later, and on simple shapes with RTX rendering. The other decisions are proposals made during planning. Measurements were taken on 2026-11-02 on the project owner's computer: RTX 3080 with 10 GB, Ryzen 7 3700X, 64 GB of memory, and driver 610.88.

## Kit installation

- **Decision**: `kit-app-template` at commit `b8e9f2e`, which uses Kit 110.4.1, cloned outside the repository to `C:\dev\omniverse\kit-app-template` by default. `setup.ps1` stops and points to the license terms if they have not been accepted, and it never accepts them on a user's behalf.
- **Rationale**: NVIDIA's current instructions install Kit this way, and the fixed commit makes setups repeatable. The SDK and its extensions take several gigabytes and must not enter the repository. Acceptance is a decision for each user.
- **Alternatives considered**: The Omniverse Launcher does not appear in the current instructions. Isaac Sim adds robotics features that this feature does not need.

## Where the code lives

- **Decision**: One Kit extension in `omniverse/exts/highbay.replay`, started with the repository's own `highbay.replay.app.kit` and `--ext-folder`. The template's Kit Base Editor is built once by `setup.ps1`, so that its downloads provide the dependencies.
- **Rationale**: The feature's code is versioned with the project, and nothing in the repository depends on files generated by the template. The application definition also keeps data collection off, as the project owner decided.
- **Outcome**: Starting the `.kit` file from the repository works. The application file must not share its name with the extension, as Kit treats an application as an extension too, and reports a circular dependency. It is therefore `highbay.replay.app.kit`. The template's `extscache` is a further `--ext-folder`, so that dependencies resolve without asking the online registry first.
- **Alternatives considered**: A custom build through the template's `premake5.lua` changes files outside the repository with each change to the application.

## Sharing logic with the browser viewer

- **Decision**: Copy the behavior of `replay-state.js`, `motion.js`, `layout.js`, `playback.js`, and `picking.js` into Python modules with no Kit imports, and compare them with the JavaScript modules at sampled times in headless Chromium.
- **Rationale**: This satisfies FR-006 and SC-002 and makes the logic testable without Kit. The state rule stays the same as in the browser: events are applied in order, and moving backward starts again from time 0, so the state depends only on the time.
- **Alternatives considered**: See the plan's complexity tracking.

## Scene structure

- **Decision**: Y up, 1 unit per meter, and the same axes as `layout.js`. One `PointInstancer` has one instance per cell and one prototype per article color, using the browser's fixed sequence of colors. Empty cells are hidden through `invisibleIds`. Rack uprights and beams use a second instancer. Each crane is a small group of ordinary prims.
- **Rationale**: Instance count stays fixed, so an update only touches what changed. Individual prims for 100,000 load units would make scene creation and updates far slower.
- **Alternatives considered**: Rewriting positions on every change has a higher cost with no gain. Lines for rack frames, as in the browser, carry little meaning under RTX lighting, and they do not cast shadows.

## Measured performance

A prototype with 100,000 instances and 20 cranes, at 1920×1080 in RTX Real-Time mode, with the frame limiter and eco mode off:

| Case | Windowless | With a window |
|---|---|---|
| Scene creation | 1.4 s | 1.4 s |
| RTX ready, shaders already compiled | about 26 s | about 18 s |
| No changes | 260 fps | 254 fps |
| 20 cranes moving | 66 fps | 73 fps |
| Cranes, plus crane colors once per second | 67 fps | 69 fps |
| Cranes, plus `invisibleIds` changing in every frame | 37 fps | 40 fps |
| Cranes, plus `protoIndices` changing in every frame | 37 fps | 42 fps |

- **Consequences**: The targets in SC-003 and SC-004 look reachable. Updates cost 8 to 10 ms per frame in Python, mostly for moving 20 cranes one attribute at a time, so `scene.py` should batch them in one change block.
- **Limits of this measurement**: The camera was close to the racks, so only part of the warehouse was in view. There were no rack frames, floor, or display window, and no state calculation. These numbers do not prove SC-003 or SC-004, and the performance tests in Kit must measure them with the whole warehouse in view.
- **Not measured**: Time to load the planning-target recording, and moving to a time in Python. The small sample has 14,577 events and takes 1.3 MB, so SC-005 appears to have ample room. A performance test measures it.

The frame limiter and eco mode stay at Kit's defaults in normal use. The tests switch them off to measure capacity.

## Closing Kit

- **Finding**: After `app.post_quit(0)`, Kit did not end within 45 seconds in any of four runs, with or without a window, and with `--/app/fastShutdown=true` too. Runs ended by a watchdog calling `os._exit` left no process behind. The cause is unknown.
- **Decision**: Automated Kit tests write their results to a file and end with `os._exit`, under an outer time limit. A manual step in the quickstart checks that closing the window ends the application.
- **Outcome**: Sending the window a normal close request ended Kit and `run-replay.ps1` in about 1 second in three runs, and within about 20 seconds in the first, leaving no process each time. Only a request to quit from a script is affected, so no fix is needed for planners.

## First replay in the application

Measured on `out/small` with a window, at the default update rate and with shaders compiled: 10.6 seconds from the command to an open run, and about 116 frames per second while playing at 600×. A windowless replay of `out/small-stepped` gave about 116 frames per second too. These do not replace the measurements for SC-003 and SC-004 in the performance tests.

Kit's viewport grid and light icon stay visible. Both can be switched off in the viewport's own menu, and they do not affect any requirement.

## State interface

- **Decision**: One small interface: describe the warehouse, tell the available time range, give the state at a time, give the cells changed since the last call, and give details of one cell or load unit. Sources declare whether they can move backward and whether their time range is final. See [contracts/state-interface.md](contracts/state-interface.md).
- **Rationale**: A live source can provide the same data with only the current time available, and display code only uses the interface. A scripted source with a growing time range and no way to move backward proves this (SC-007). There is no write operation, which matches Principle IV.
- **Alternatives considered**: Using the plant model's signal list directly would limit the display to time-stepped runs, and signals have no backlog or order data.

## Selection

- **Decision**: A click in the viewport creates a ray from the camera. The ray finds cranes by their boxes, and cells with `picking.py`, with the same rules as the browser.
- **Rationale**: One instancer with 100,000 instances has no useful per-instance selection in the stage, and a calculated ray also finds empty cells.
- **Risk**: Getting a click and camera ray from the viewport in Kit 110 was not prototyped, so the task for it must try this first. As a fallback, the window offers a list of cranes and entry fields for a location.

## Looks

- **Decision**: `appearance.py` has one function per object type. An optional setting per type names a USD file to reference in place of the simple shape. If the file cannot be loaded, the simple look is used and a warning names the type.
- **Rationale**: This satisfies FR-013 and its edge case, without needing any models now.

## Tests and Kit's Python

- **Decision**: Project tests import only `core/` through a new pytest path. They run under Python 3.14 and, in one documented command with `uv run --isolated --python 3.12`, under 3.12, which leaves the project's environment alone and downloads Python 3.12 on first use. Kit tests start the real application with a test script and read a results file. They run only on request with `-m omniverse`, because they take minutes and occupy the graphics card.
- **Rationale**: Normal test runs stay fast and need no graphics card, and SC-008 stays true. Running under 3.12 catches syntax that Kit could not load.
- **Software version**: Goes to 0.4.0 as with earlier features. It only changes the recorded version in results, which existing reference tests leave out.

## Data collection

- **Decision**: `highbay.replay.app.kit` sets `telemetry.enableAnonymousData = false`, as the project owner decided. `setup.ps1` sets the same value in the template's generated application, so that no application in the setup collects data. The README states this.
